# Catalna playable prototype — implementation status (2026-10-28)

Continues `03541b2c` (WIP checkpoint). Read with
`prototype_license_evidence.md` and `prototype_asset_measurements.json`.

## What this slice is

`game/main.blend` (scene `CatalnaCreek`): a 180 m straight creek with banks and
meadows, nine rock obstacles, procedural shoreline vegetation, a checkpoint and
finish banner, the approved Quaternius inflatable rubber raft with two oars, a
follow camera and two HUD text objects. `game/prototype_entry.py` is the only
engine-facing gameplay loop; all rules live in `src/rr/core/prototype.py`.

Loop: menu → paddle downstream → bump rocks (hull damage, forgiving respawn at a
mid-river checkpoint) → finish → restart or quit. Pause and quit are wired.

## Raft proportions: resolved by rescaling, not by distortion

The committed asset `RF_RaftT1.blend` is the Quaternius hull squashed
non-uniformly into a historical 2.4 × 3.2 × 0.4 m box. The builder undoes that
squash and applies **one uniform factor to the original GLB**:

| | width | length | height |
|---|---|---|---|
| original GLB | 11.9641 | 23.6451 | 4.3020 |
| runtime raft | 2.4287 | 4.8000 | 0.8733 |
| ratio | 0.2030019 | 0.2030019 | 0.2030019 |

`build_prototype.py` asserts the three ratios agree to 1e-6 and
`verify_prototype_scene.py` re-checks them from the saved file, so a distorted
hull cannot be reintroduced silently.

Dependent values were updated coherently in `game/settings/prototype.json`
rather than keeping the old 3.2 m number: a 4.8 m hull displaces more, so the
heave spring is `stiffness 24000 N/m` with `damping 2700 N·s/m` and
`max_force 9000 N`. That puts equilibrium at `m·g/k = 2943/24000 = 0.1226 m`
draft, which still matches the 0.12 m target in `docs/07` §2, and the body spawns
at that exact height so it does not bounce on load. `yaw_drag` rose to 500 for
the longer hull. The collider is a BOX at the runtime dimensions; roll and pitch
are locked and yaw is free, which is what `rr.core.prototype.forces` models.

**`docs/07` was not edited.** Its 2.4 × 3.2 × 0.4 collider and six-sample
buoyancy still describe the V-01/V-02 production raft. This slice uses its own
tunables file and a single equivalent heave spring; reconciling the two is
production work, not a prototype decision.

## Three UPBGE defects found by actually running it

The checkpoint's builder had never been executed in UPBGE. Running it exposed:

1. `scene.render.engine = "BLENDER_EEVEE_NEXT"` — not a valid enum in UPBGE 0.50
   (`BLENDER_EEVEE`, `BLENDER_WORKBENCH`, `CYCLES`). Fixed.
2. `body.game.use_rotation_x/use_rotation_y/use_sleep` — `use_rotation_*` does not
   exist. The real names are `lock_rotation_x/y/z`, and they are inverted: setting
   `True` locks the axis. `use_sleep` is "No Sleeping", so `True` is what keeps the
   raft awake. The checkpoint set all three to `False`, which locked nothing and
   allowed sleeping. Fixed and asserted in the scene verifier.
3. `bpy.ops.logic.sensor_add` — **EXCEPTION_ACCESS_VIOLATION under `-b`**, even
   with a full `temp_override`. Windowed without an override it fails
   `poll() Context missing active object` (same cause as S-01 §6.7). Windowed
   **plus** `temp_override(window, screen, object, active_object)` works.

Because object-creation operators need background mode and logic operators need a
window, the build is now two passes plus a verification pass, orchestrated by
`tools/build_prototype_scene.py`. `wire_prototype_logic.py` exits with `os._exit(0)`
because `bpy.ops.wm.quit_blender()` access-violates on shutdown in this build
(and hangs if the netlogic addon is disabled first), so its exit code is not
evidence. Success is decided by stdout markers and by pass 3 reopening the file.

A fourth defect was found at runtime: **`KX_FontObject` exposes no `text`
attribute** in this build (the only name-matching members are
`disableRigidBody`/`enableRigidBody`). The HUD now resolves a setter at runtime
and falls back to `obj.blenderObject.data.body`, which worked when exercised in
blenderplayer. It degrades to a logged message instead of killing the loop.

## `game/main.blend` is deliberately NOT in this commit

Catalna holds the Git LFS lock on it (`git lfs locks` → `game/main.blend
Catalna ID:59663331`), and `*.blend` is `lockable` in `.gitattributes`, so
pushing it was rejected:

```
Unable to push locked files:
* game/main.blend - Catalna
```

Per `AGENTS.md` rule 4 the lock holder owns that file, so it was dropped from
the commit rather than forced through. It is fully regenerable from committed
sources in one command, and `prototype_asset_measurements.json` records the
SHA-256 of each source `.blend` the scene was built from:

```bash
export UPBGE_PATH=/path/to/upbge-0.50          # folder with blender + blenderplayer
python tools/build_prototype_scene.py          # builds, wires and verifies
```

The scene was built and verified locally from exactly this commit's sources
(2 836 960 bytes, `VERIFY_OK`, `problems: []`).

### Asset-gate false-pass fix preserved

The checkpoint's fix is intact: the gate now requires `[validate] 0 problem(s)`
in stdout **and** a zero exit **and** no `FAIL` line, with `--python-exit-code 1`.
Its four regression tests still pass. One additional bug was fixed: the gate
passed `/mnt/c/...` paths to a Windows `blender.exe`, which cannot open them, so
every asset failed. `run_game.host_path()` now translates paths via `wslpath`,
with three new regression tests.

## Blocked: runtime gameplay on this host

The game **was launched** through the real entry point
(`python tools/run_game.py game/main.blend --smoke --seconds 8`). Confirmed from
the player console:

- `prototype_entry` imported and `tick` ran.
- `Session` constructed inside UPBGE: settings loaded, `PrototypeAudio` built,
  scene objects resolved by name, collision callback registered.
- The HUD text write succeeded through `blenderObject.data.body`.

Then the engine died before the smoke window elapsed:

```
GL_VENDOR: ATI Technologies Inc.
GL_RENDERER: AMD Radeon(TM) Graphics
gpu.shader | ERROR eevee_light_culling_tile Linking: Compute link error: HW_UNSUPPORTED.
gpu.shader | ERROR eevee_light_shadow_setup  Linking: Compute link error: HW_UNSUPPORTED.
```

UPBGE 0.50's EEVEE compute shaders are unsupported by this AMD integrated GPU.
Forcing `BLENDER_WORKBENCH` did not help: the game engine initialises EEVEE
regardless, and the same two shaders fail. So **no frame-stepping gameplay,
sustained physics, audio playback, collision response or end-to-end loop has been
observed on P1's machine**, and `smoke_result.json` was never written. This is
the same machine class that produced the S-01 blenderplayer crash.

`game/prototype_entry.py` carries a smoke mode (`RR_SMOKE=1`) that autopaddles
for a fixed time and writes measurements, so Catalna can produce that evidence in
one command on Tier A hardware.

## Not verified / outstanding

- **Audio aesthetics** — never auditioned; all cues are structurally valid placeholders.
- **HUD legibility and layout** — the text objects are parented in camera space with
  computed extents, but nothing has been seen rendered.
- **Camera framing, raft handling feel, difficulty** — require play.
- **Quaternius CC0 vs QAL** — still unresolved, see `prototype_license_evidence.md`.
  Nothing here settles it; the generated audio is own-made and unaffected.
- **`docs/07` reconciliation** — the slice's single-spring heave and 4.8 m hull
  differ from the production six-sample spec. Deliberate, and left to V-01/V-02.
- **Vegetation** is original procedural cones, not the Quaternius MegaKit trees,
  which all exceed the 800-triangle `EN_PineTree` budget. No budget was changed.
